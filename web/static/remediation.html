Zen Harness Remediation

What is wrong, in the order it should be fixed — across the data engine, the engineering around it, and the agent loop. Nothing here defends the current codebase; every item was found by reading it or measuring its output.

The verdict

This is strong prototype engineering and it is not yet an organization's harness. The difference is not sophistication — the model boundary, the provenance chain and the coercion markers are better than a lot of production ML tooling. The difference is that an org harness assumes nobody is watching. CI catches what a person misses, containers make it run elsewhere, logs explain failures nobody saw, retention satisfies a lawyer. This codebase currently assumes a person at a terminal.

In one day, three separate instruments confidently reported false state: a supervisor called a crash-loop healthy, a metrics recorder reported a busy pipeline idle, and a diagram misdescribed the pipeline it documented. All three shared a shape — nothing in the build could contradict them.

And three findings about the data itself

90% of the corpus carries no metric signal. 661 corrected turns all cite a rule — that part works perfectly. But 6,501 kept turns were never scored against anything. The eval taxonomy justifies changes; it does not describe the data.

Tool-calling turns are barely refined. Of 271 turns carrying a tool call, only 17 were corrected — and 71 say something like "hmm" or "one minute" while invoking get_bookings_by_pnr. Train on that and the model learns to grunt while calling tools. Only 17% of conversations contain any tool call at all.

Agent selection does not do what you asked. It currently rotates by language to spread the corpus. You asked for highest-conversation-count first. These genuinely conflict: high-volume agents are production-proven but concentrate the corpus on a few deployments. The plan resolves it rather than silently picking one.

The agent loop, measured against Claude Code and Codex

The mill is deterministic and works. The agent above it exists to investigate the mill, and has completed exactly one real run in its life. That run spent seven turns searching the filesystem for data that lives in SQLite, and reached no conclusion. The reasons are structural, not incidental.

CapabilityHereConsequence
parallel tool calls absent — "tool": string|null, one per turn Investigating a cluster needs six serial round trips instead of two. With max_turns: 20 a third of the budget goes on I/O.
context compaction absent — hard truncation only value[:max_chars] cuts mid-sentence, mid-JSON. The most recently appended material is what gets destroyed.
rolling state absent — observations[-8:] At 40 turns the agent sees the last 8 observations and nothing from turns 1–32. No summary. It cannot know what it already tried.
tool result bounding absent — results inlined raw query_ledgers can return 400 KB into a 120 KB budget, silently evicting the objective and every prior finding.
token accounting absent — budgets in characters A measured language bias. See below.
streaming absent A ten-minute agent turn is a black box.
interrupt / steer absent A running agent cannot be redirected.
tool retry absent One transient failure ends that investigation path.
plan tracking absent — PLAN_SCHEMA exists, never updated No todo state carried between turns.
graph engine dead — 205 lines, 0 imports, 0 graphs zen-graph is a shipped entry point for a subsystem nothing uses. Delete it.

Character budgets are a language bias, and it is measurable. Every budget in the agent loop counts characters (max_prompt_chars = 120_000); nothing counts tokens. Measured across the corpus: English 1.05 bytes/char, Hindi 1.29, Bengali 1.48, Malayalam 1.62. The same nominal budget is a materially smaller budget for Indic languages — the agent's effective context silently shrinks for exactly the languages the corpus was widened to include.

What is genuinely right, briefly. Memory is wired and read back (read_curated(), query(scope="project")). Delegation runs in parallel. PreToolUse / PostToolUse hooks can block a call. Manifest allowlists and tool-call budgets are enforced. Sessions persist and resume. That is a real skeleton — roughly Claude Code in its first month.

And the harder conclusion

The agent is not on the critical path, and fixing it is the wrong next investment. The four missing capabilities are one refactor of the same loop — perhaps a week — and they buy you a better debugging assistant. They buy the corpus nothing.

Meanwhile 90% of the corpus carries no metric signal, tool-calling turns say "hmm" while invoking a backend, and no eval loop proves any of it improves a model. For an organization preparing training data, that ordering is not close.

Phase 2 — Make the data defensible

The three things you named, plus the one that validates them

~1 week
2.1The eval loopdata

Still the largest gap in the system. Nothing answers whether a model trained on this improves, so every quality claim — including all of mine — is unfalsifiable. Today proved the cost: every automated gate passed while half the corpus carried turns that were not speech.

1. hand-label 200 turns, stratified across judge verdicts
2. measure verifier and judge against them → precision/recall
3. fine-tune on 1,000 rows, compare to baseline on held-out calls
4. only then scale
2.2Agent selection: volume first, then spreaddata

Resolve the conflict explicitly rather than picking one. Rank by conversation count as you asked, then cap how much any single agent or project may contribute, so a handful of deployments cannot become the corpus.

rank agents by conversation_count DESC
take in order, subject to:
  ≤ 3% of the batch from any one agent
  ≤ 8% from any one project
  every language present in the inventory gets a floor
record the realised distribution in the batch manifest
2.3Score every turn, not just corrected onesdata

90% of the corpus carries no metric signal. A kept turn is an implicit claim that it was good — make the claim explicit and checkable, and the taxonomy starts describing the data rather than only justifying edits.

auditor emits a per-turn verdict against the applicable variants
kept turns carry PASS citations; corrected turns carry the failure
batch manifest reports taxonomy coverage over the whole corpus
cost: roughly 1 extra call per conversation, not per turn
2.4Treat tool turns as a first-class casedata

71 of 271 tool-calling turns say almost nothing while invoking a backend. The refiner corrected 17 of them. This is the exact behaviour you want the fine-tune to learn, and it is the least supervised part of the corpus.

refiner contract: a turn carrying a tool call must also carry a
  natural holding phrase in the caller's language — never silence,
  never narration of the call itself
new deterministic check: tool_call present + spoken text < N chars
  → flag for correction rather than pass
acquisition: prefer agents whose traces contain tool calls
  (17% today is too thin to teach tool use)
2.5Preference pairs, not just SFTdata

You generate 661 (source, golden, cited-rule) triples and ship only the golden half. The rejected side is the more informative one, and it is already on disk.

export v4-preference.jsonl: {prompt, chosen, rejected, rule}
judge-rejected pairs included with polarity inverted

Phase 3 — Make it survive absence

The difference between a prototype and a system

~1 week
3.1Structured logging and a circuit breakerengineering
replace 125 print() with logging, JSON handler, levels
delete the 12 except:pass swallows — log and re-raise, or handle
circuit breaker: N consecutive identical failures → pause the run
  and alert, instead of spending attempt budget on a billing error
3.2Delete the string-matching testsengineering

Twelve test files assert that certain characters exist in source. They pass when the code is broken and fail on a harmless rename. They give false coverage, which is worse than none because it stops the real test being written.

3.3The agent loop: one refactor, not fourengineering

Parallel tools, compaction, token budgets and rolling state are the same loop touched four ways. Do them together or not at all. Ranked last deliberately: this buys a better debugging assistant, not better data.

ACTION_SCHEMA: tool_calls[] instead of tool, executed in parallel
observations: rolling summary + last N, not a bare [-8:] window
tool results: cap rows and bytes at the broker, not in the prompt
budgets: count tokens, not characters (Malayalam is 1.62 bytes/char)
delete graph_runtime.py and the zen-graph entry point
3.4Migrations, backups, and one honest guideengineering
schema_version table + forward migrations for 11 stores
nightly backup of .zen/*.db, restore verified in CI
rewrite GUIDE.md or delete it — it describes a system that is gone
split or remove the 3,456-line agent kernel the factory never imports
Every item above came from reading the code or measuring its output on 2026-08-20, against run 389362df at 809 candidates. The ordering is deliberate: Phase 1 makes the system safe to change, Phase 2 makes its output defensible, Phase 3 makes it survive nobody watching. Doing Phase 2 before Phase 1 means fixing data quality on a codebase where nothing catches a regression.
